## Causal EE SQRT operand fix

The raw bytes rule out GIF color-latching as this discrepancy's cause. Every
PACKED A+D RGBAQ in submissions 1141..1156 literally contains RGB `602618`:
1,024 constant-color writes, not incorrectly decoded packed color descriptors.
The EE packs that color near `00219CB8`..`00219D04`, after reading the brightness
word at offset 8 of its cloud table entry. Endpoint PC `0027395C` is a later
matrix helper, not the color writer.

A separate eight-instruction-slice probe reaches submission 1144 at exactly
`260451479`/`0027395C`; all first 1,144 payloads, boundaries and EE metadata match
the one-step tracer. The concatenated 1,142,880 payload bytes have SHA256
`1225243aff7007c486071697c7771d1c04c69dfd0577c5442d237d79a3e53d81`.
Its ignored RAM snapshot shows all 289 brightness entries at `00344940` equal
96, with entry words `(0,0,96,128)`.

The table updater computes squared distance into `f12`, then executes SQRT at
`00219740`; an earlier radius SQRT is at `002195C4`. Both encode `ft=f12` and
`fs=0`, with destinations `f2` and `f20`. Astra incorrectly evaluated `sqrt(fs)`.
R5900 **SQRT.S fd,ft** reads bits 20..16, unlike the ordinary unary COP1 source
in bits 15..11. This routing is independently checked against the
[pinned primary PCSX2 operand definitions and SQRT implementation](https://github.com/PCSX2/pcsx2/blob/v2.8.2/pcsx2/FPU.cpp#L334-L344).
The production fix changes only this SQRT operand to `ft`; it does not pretend
host IEEE arithmetic implements all PS2 negative-input, flag, denormal,
saturation or rounding behavior.

Decoded table arithmetic and captured globals independently predict 261 zero
brightness entries, and two entries for each blue value
`5,6,9,13,15,19,24,31,40,43,46,50,69,76`. These are precisely the fourteen
nonzero blue values in the saved reference cloud draw, with matching
multiplicities. This connects the missing radial mask to a specific instruction
operand error. Post-fix capture and matched-input results follow below.

The owned EE FPU regression has **42 checks**: nine SQRT routing/alias/signed-zero
cases, unchanged ABS/MOV/NEG `fs` controls, and a 23-instruction radial program
executed for all 289 cells. Its separate double-precision geometric oracle checks
integer brightness bins, not native PS2 float bit identity. The preserved
pre-fix core fails **10 checks**; the fixed core passes all 42. The ordinary
nonperfect square root accepts an adjacent float instead of overclaiming PS2
rounding behavior.

## Reference STQ precision calibration

The apparent low-bit float mismatch must not trigger an EE/VU arithmetic patch.
PCSX2's `FlushPrim` masks STQ **before** printing the saved `GSVertex` words,
for textured STQ draws with sprite class or equal-Z tracing. The pinned source
has no texture-size/filter or software-only gate. Saved draw 81 reports equal Z.
See [the primary precision/dump ordering](https://github.com/PCSX2/pcsx2/blob/v2.8.2/pcsx2/GS/GSState.cpp#L2333-L2467).

The explicit comparator `--pcsx2-gs-precision` view applies that observed finite
precision rule to copies. For all 714 aligned vertices, raw S/T/Q differences
`714/534/714` become **0/0/0**, with no exceptional inputs skipped, both before
and after the SQRT fix. For example Q `3C0AF5E4` becomes saved `3C0AF500`; S
`3C0AAB30` becomes `3C0AAA00`. This is compatibility with saved GS precision,
not proof of identical incoming original floats. RGB is not transformed, so its
before/after discrepancy remains a separate, valid causal observation. Raw
trace words and `--require-equal` behavior are unchanged; incomplete geometry
and omitted state still prevent whole-draw equality claims.
